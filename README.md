# orders-aggregator

Сервис загружает заказы внешнего магазина, принимает вебхуки и считает дневную статистику клиентов. Интерфейс построен на React, TypeScript, Vite и shadcn/ui.

## Запуск одной командой

Нужны запущенный Docker Desktop с Linux-контейнерами и Node.js 20+ для скрипта запуска. Для локальной разработки фронтенда используйте Node.js 22 LTS.

Если образ `orders-mock:3` ещё не загружен, положите приложенный к заданию архив `orders-mock-amd64.tar.gz` или `orders-mock-arm64.tar.gz` в корень проекта либо рядом с его папкой. Скрипт выбирает архив под архитектуру Docker и загружает образ.

Из корня проекта выполните.

```bash
npm run up
```

Скрипт собирает приложения, поднимает PostgreSQL, внешний API, наш API и frontend, затем ждёт проверок готовности. Миграции применяются при запуске API. Данные сохраняются в именованном Docker volume.

- Интерфейс — [localhost:3000](http://localhost:3000/).
- Наш API — [localhost:3001](http://localhost:3001/health).
- Внешний тестовый магазин — порт `4000`.
- PostgreSQL — порт `5432`, базы `orders` и `orders_test`.

Это локальное окружение с тестовыми учётными данными PostgreSQL. Порты должны быть свободны. Настройки аутентификации и публичного production-развёртывания потребуют отдельной подготовки.

Остановка с сохранением базы.

```bash
npm run down
```

## Страницы

`/orders` показывает сохранённые заказы: до скидки, скидку в рублях и процент (если передан), сумму после скидки, статус и даты. По умолчанию 50 записей на страницу, доступны 10/20/50/100, переход к первой/последней странице и счётчик общего количества. Кнопка «Обновить заказы» выполняет полный `POST /sync`, затем обновляет таблицу. Если часть данных сохранилась перед ошибкой, таблица также перечитывается, а сообщение об ошибке остаётся видимым.

В каждой строке есть «Посчитать сумму». Окно получает ID клиента из заказа, позволяет выбрать обе даты и показывает gross, discount, net и перечень оплаченных заказов, вошедших в расчёт. Список запрашивается с сервера страницами; сумма и количество учитывают весь период.

`/logs` показывает результат последней проверки данных.

- Таблица скидок содержит только расхождения между `amountPaid` и оплатой, рассчитанной по `discountPercent`.
- Проверка клиентов сопоставляет текущую статистику с независимым пересчётом PostgreSQL по одному снимку заказов.
- Отличия прежнего алгоритма часовых поясов показываются отдельно с пометкой «Прежний алгоритм».
- По умолчанию проверяются 27–31 марта 2026 года, включая клиента `c_7`. Период можно изменить.
- Записи старого формата и неполные данные учитываются отдельными счётчиками. Ошибки клиентов изолируются, остальные проверки продолжаются.

Это таблицы текущей проверки. Все четыре таблицы используют TanStack Table v8 с серверной пагинацией. Списки ошибок скидок и клиентов имеют независимые страницы, сводные счётчики относятся ко всей проверке. Отдельного отчёта платёжной системы у проекта нет.

При первой загрузке видны skeleton-заглушки, при обновлении остаются прежние данные с индикатором загрузки, кнопки показывают выполнение и блокируют повторный запрос. После ошибки без полученных данных показывается ошибка с повтором, без утверждений о пустой выборке. Окно плавно открывается и закрывается (200/130 мс), возвращает фокус к кнопке строки, закрывается по Escape. Настройка reduced motion отключает движение.

## API

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/health` | Живость приложения |
| POST | `/sync` | Полная синхронизация, ответ после завершения |
| POST | `/webhooks/order` | Создание или обновление заказа, повтор/старая версия возвращает stale |
| GET | `/orders?limit=50&offset=0` | Список сохранённых заказов, limit от 1 до 100 |
| GET | `/customers/:id/daily-totals?from=YYYY-MM-DD&to=YYYY-MM-DD` | Дневные total, gross, discount, net |
| GET | `/customers/:id/daily-totals?...&includeOrders=true` | Итоги периода, дневная статистика и учтённые заказы |
| GET | `/diagnostics?from=YYYY-MM-DD&to=YYYY-MM-DD` | Проверка скидок и клиентов |

Параметры пагинации.

- `/orders?limit=50&offset=0` возвращает `{ items, total, limit, offset, hasMore }`. В записи добавлены `amountPaid`, `discount`, `discountPercent`; `amount` остаётся суммой до скидки.
- `includeOrders=true&ordersLimit=20&ordersOffset=0` возвращает страницу `orders` и `ordersPagination: { total, limit, offset, hasMore }`. Итоги `daily/gross/net/discount/total` считаются по всему периоду. Без `ordersLimit` сохраняется полный список для совместимости.
- `/diagnostics?...&discountLimit=50&discountOffset=0&customerLimit=50&customerOffset=0` ограничивает два списка отдельно и возвращает `discountPagination`/`customerPagination`. Без limit соответствующий список полный. Проверка выполняется по всему снимку на каждый запрос, затем ограничивается выдача; это не оптимизация стоимости самого пересчёта.
- Все limit — целые 1..100, offset — неотрицательное безопасное целое. Ненулевой offset требует соответствующего limit.

В React запросы идут на `/api/...`. Nginx проксирует их в API. Для прямых запросов используется порт `3001`.

`gross` и совместимое поле `total` — стоимость оплаченных заказов до скидок. `net` — фактическая оплата. `discount = gross - net`. Суммы возвращаются в рублях, внутри хранятся в целых копейках. Границы периода включительны, день определяется по `createdAt` в таймзоне клиента.

Ошибки приложения возвращаются как `{ error, message }`.

## Вебхуки и result.json

После завершения синхронизации отправьте тестовые вебхуки.

```bash
npm run webhooks
```

Команда направляет их на `http://api:3000/webhooks/order` внутри Docker-сети. При запуске бэкенда на хосте подходит исходная команда.

```bash
docker compose run --rm orders-api webhooks --target http://host.docker.internal:3000/webhooks/order
```

Для повторного получения результата задания нужна отдельная чистая БД. После запуска, полного sync и завершения вебхуков сохраните ответ.

```bash
curl -f "http://localhost:3001/customers/c_7/daily-totals?from=2026-03-27&to=2026-03-31" -o result.json
```

Готовый `result.json` получен именно в этом порядке. Подробности проверки приведены в `SOLUTION.md`.

## Тесты и сборка

Полный набор бэкенд-тестов в отдельной тестовой базе внутри Docker.

```bash
npm run test:docker
```

Локальные проверки при работающем PostgreSQL.

```bash
npm run install:all
npm run typecheck
npm test
npm run build
```

Тесты очищают только таблицы базы `orders_test`.

Для локальной разработки API выполните `npm run dev:backend` из корня. Миграции вручную — `npm --prefix backend run migrate`. Он работает на порту `3000` по умолчанию. В другой консоли запустите `npm run dev:frontend`, интерфейс будет на `5173` и проксирует `/api` на `3000`. Если используете уже запущенный Docker API на `3001`, задайте для Vite `API_PROXY_TARGET=http://localhost:3001`.

## Структура проекта

```text
orders-aggregator/
  backend/       сервер, src, test, migrations, Dockerfile, package.json и lock
  frontend/      React-приложение, Dockerfile, package.json и lock
  scripts/up.mjs общий запуск и загрузка внешнего Docker-образа
  docker-compose.yml
  package.json   команды для обоих приложений
  TASK.md, README.md, SOLUTION.md, IMPLEMENTATION_REPORT.md, result.json
```

Оба приложения устанавливаются и собираются независимо. В корневом package.json нет зависимостей, он перенаправляет команды в нужные каталоги. Docker-контексты — ./backend и ./frontend; SQL создания тестовой БД находится в backend/scripts. Локальные .env и .env.example сервера также находятся в backend/.

## Архитектура React

```text
frontend/src/
  app/        провайдеры, store, маршруты и глобальные стили
  pages/      страницы orders и logs
  widgets/    оболочка, таблица заказов и блок диагностики
  features/   синхронизация, окно отчёта, пагинация, фильтр логов
  entities/   модели и API заказов, клиентов и диагностики
  shared/     HTTP-клиент, форматирование, базовые UI-компоненты
```

React Router отвечает за маршруты. TanStack Table управляет таблицами в режиме manualPagination, метаданные страниц поступают с сервера. TanStack Query хранит серверные данные и управляет запросами. Redux Toolkit slices хранят выбранную страницу, клиента и периоды формы. Между сущностями используются явные type-only `@x` API. Крупные блоки разделены на подкомпоненты. Компоненты shadcn/ui находятся в `shared/ui`.
