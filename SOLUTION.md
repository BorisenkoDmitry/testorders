# Решение задания

## Что реализовано

Добавлены сохранение `discountPercent` и `amountPaid`, миграция `002_order_pricing.sql` и расширенный дневной ответ `date, total, gross, discount, net`. `total` равен `gross`. В статистике участвуют только заказы со статусом `paid`.

Синхронизация и вебхуки используют один нормализатор. Суммы сохраняются в целых копейках. `amountPaid` является приоритетным источником фактической оплаты. Несовпадение с процентом фиксируется диагностикой, переданная оплата сохраняется.

Применение версии перенесено в атомарный PostgreSQL upsert. Более старая версия не перезаписывает свежую при одновременных запросах. Повторные события возвращают `stale`.

Миграция помечает ранее сохранённые записи `pricing_version = 0`. Повторный sync один раз догружает данные скидки даже при совпадающем `updatedAt`, затем обычные повторы снова пропускаются. Это также позволяет исправить прежнюю конвертацию сумм у старых записей.

Сигнатура `createContainer(db, api)` и интерфейс `OrdersApi` совместимы с исходным контрактом.

## Причина мартовского расхождения

Исходный код один раз вычислял смещение таймзоны клиента на текущую дату запуска сервера и применял его ко всем историческим заказам. Для `Europe/Berlin` это неверно на переходе к летнему времени 29 марта 2026 года.

Теперь смещение вычисляется для каждого `order.createdAt`. Выборка имеет запас по UTC-границам, после чего заказ попадает в календарный день клиента. Нулевые дни и включительные границы периода сохранены.

Причину проверили тремя способами.

1. Регрессионный тест с заказами на границах суток и переходе времени.
2. Один и тот же мартовский отчёт проверен при системной дате в январе и июле.
3. PostgreSQL независимо группирует тот же снимок заказов через `AT TIME ZONE` и сверяет все поля дневного ответа.

На финальном снимке после вебхуков прежний алгоритм и правильный расчёт для `c_7` различаются так.

| Дата | Прежний total на том же снимке | Исправленный gross |
| --- | ---: | ---: |
| 2026-03-29 | 43964 | 34658 |
| 2026-03-30 | 52201 | 59684 |
| 2026-03-31 | 44064 | 35401 |

После исправления все 40 клиентов совпали с независимым пересчётом за выбранный период. Ещё два отличия прежнего алгоритма проявились у клиента `c_23` с `America/New_York`.

## Дополнительная ошибка денежных сумм

`Math.floor(rub * 100)` терял копейку из-за двоичного представления дробей. Например, `19.99 * 100` даёт `1998.9999999999998`, после floor получалось `1998`.

Перевод теперь выполняется через десятичное представление и BigInt. Он поддерживает числовые строки и экспоненциальную запись, отбрасывает настоящие доли копейки согласно исходному контракту и отклоняет переполнение безопасного целого.

Это отдельный дефект, важный для новой статистики оплаты. Исходная жалоба по дневным суммам до скидок воспроизводится ошибкой часового пояса.

## Допущения

- Если оба новых поля отсутствуют, заказ считается старым форматом без скидки. В живом API найдено 1177 таких заказов.
- Если есть `amountPaid`, используется его значение, включая ноль.
- Если оплаты нет, но процент есть, net вычисляется по проценту. Диагностика показывает такие данные как неполные. В контрольном наборе таких случаев нет.
- Для проверки процента и этого fallback выбрано округление к ближайшей копейке, половина вверх. TASK.md не задаёт правило округления.
- Проверка скидки — проверка арифметики. Отдельный отчёт платёжной системы не предоставлен, поэтому фактическое списание денег независимо не подтверждается.
- Диагностика отражает последний снимок сохранённых данных. Это не накопительный исторический журнал.
- Источником дня является `createdAt`, как в исходном сервисе.

## Проверка результата

На новой чистой базе в именованном volume выполнили полный порядок из задания.

1. `npm run up` собрал и поднял четыре сервиса, все проверки готовности прошли.
2. Счётчик заказов до sync был нулевым.
3. Кнопка React выполнила `POST /sync`. Получены 5030 заказов за 52 страницы, синхронизация завершилась.
4. `npm run webhooks` отправил 92 события. Все 92 получили HTTP 200, включая допускаемые повторы и старые версии.
5. Сохранён стандартный ответ для `c_7` за 2026-03-27–2026-03-31 в корневой `result.json`.
6. Для каждого дня проверены `total = gross`, `discount = gross - net` в копейках и совпадение сумм с перечнем учтённых заказов.
7. Диагностика проверила 5030 заказов, включая 3853 с обоими полями скидки, и 40 клиентов. Ошибок скидки 0, текущих ошибок клиентов 0.

Итог за период для `c_7` — 44 оплаченных заказа, gross 212712 ₽, net 184904.66 ₽, discount 27807.34 ₽.

До контрольных вебхуков была сохранена исходная статистика работающей старой версии. Прямое сравнение её значений с финальным файлом включает также законные изменения статусов и версий от вебхуков. Для выделения ошибки даты использована таблица выше, где оба алгоритма работают на одном финальном снимке.

## Тесты

Локально и через `npm run test:docker` прошли 60 тестов в 9 файлах. Проверены.

- Полная синхронизация, невалидные записи и конец cursor-пагинации.
- Создание, обновления, повторы и устаревшие вебхуки.
- Одновременное применение версий и конкурентные дубликаты.
- Однократное обогащение записей после миграции.
- Новые, старые и частичные поля скидки, нулевая оплата, неверные проценты и суммы.
- Копейки, десятичные строки, экспоненциальная запись, округление и переполнение.
- Дневные gross/net/discount/total, статусы, клиент, границы периода и пустые дни.
- Переход летнего времени и независимость результата от текущей даты сервера.
- Отбор заказов подробного отчёта и совместимость стандартного ответа.
- Независимая SQL-проверка, намеренно внесённая ошибка агрегатора, ошибки клиентов и один снимок при параллельном поступлении данных.

`npm run typecheck` проверяет оба приложения, `npm run build` собирает оба (для Vite используйте Node.js 22 LTS). Production-сборки обоих приложений дополнительно прошли в Docker на Node.js 22.

## Дополнительно по просьбе пользователя

Обычная HTML-страница перенесена на React + TypeScript + Vite с официальными компонентами shadcn/ui. Добавлены страницы заказов и логов, React Router, TanStack Query, Redux Toolkit slices и FSD-слои.

Страница заказов содержит синхронизацию, пагинацию и окно суммы клиента с выбором дат, итогами и списком заказов. Колонка проверки скидки в основной таблице не добавлялась. Для ошибок выделены отдельные таблицы на странице логов.

В интерфейсе отдельно помечены отличия прежнего алгоритма. При нуле настоящих ошибок отображается честное пустое состояние.

Проверены большой и узкий экран, переходы между страницами, сохранение пагинации через Redux, расчёт `c_7`, закрытие окна по Escape и возврат фокуса в кнопку строки. Проверка FSD-импортов не выявила переходов в верхние слои или неявных межсущностных импортов. Самый большой собственный UI-компонент приложения — 41 строка; общий DataTable вынесен в shared/ui и разделён с контролами пагинации.

В ходе проверки найден и устранён случай частичной ошибки sync. Инвалидация кэша перенесена в `onSettled`. Отдельный изолированный браузерный сценарий подтвердил, что после HTTP 502 частично сохранённый заказ появляется в таблице, а сообщение об ошибке остаётся видимым. Контрольная база в этом сценарии не изменялась.

Добавлены Docker-сборки API и frontend, Nginx-прокси, проверки готовности, сохраняемая база, автоматическая загрузка приложенного образа и отдельный Docker-профиль тестов. Полный запуск выполняется через `npm run up`. Подготовлены исключения для Git и lock-файлы.

Сервер перенесён из корня в backend/, frontend/ расположен рядом. В корне остались Compose, документация и пакет общих команд. Перенесены исходники, тесты, миграции, Dockerfile, env и собственные зависимости сервера; исправлены контексты сборок и путь init SQL. Образ внешнего магазина по-прежнему ищется в корне или рядом с проектом.

Основная таблица показывает сумму до скидки, скидку (рубли и переданный процент) и сумму после скидки. Для последней используется та же логика netKop, что и в статистике: оплата API приоритетна; расхождение с процентом остаётся в логах.

Все таблицы переведены на TanStack Table v8. У /orders добавлен total, count и страница читаются в одном repeatable-read снимке. У подробного отчёта добавлены ordersLimit/ordersOffset и ordersPagination. У диагностики — независимые discountLimit/Offset и customerLimit/Offset. По умолчанию старые клиенты без новых параметров по-прежнему получают полные списки. Новые параметры валидируются, максимум страницы — 100. Общие суммы и счётчики вычисляются до среза. Пагинация выдачи диагностики не сокращает объём самого пересчёта.

Добавлены skeleton для первого запроса, индикаторы повторной загрузки, сохранение прежней страницы на время запроса, состояния кнопок, анимация появления/закрытия окна и reduced motion. Исправлена ширина содержимого окна на телефоне и ложные пустые состояния при ошибке API. После неуспешной загрузки без данных отображается только сообщение ошибки с повтором.

Шесть новых регрессионных тестов проверяют DTO цен (включая несовпадение оплаты, 100% и частичные поля), полную последнюю страницу, независимость итогов от страницы подробного отчёта, независимые страницы логов и валидацию новых параметров. Все 60 тестов прошли локально и в Docker. После переноса четырём контейнерам повторно подтверждён healthy, а стандартный ответ c_7 совпал с result.json.

## Что ещё замечено и что доделать

Внешний API действительно смешивает старый формат с новым. Он ограничивает частоту запросов, иногда сигнализирует о лимите HTTP 200 с error-полем и завершает список пустой страницей с прежним курсором. Существующий HTTP-клиент и цикл sync учитывают эти особенности.

У исходных зависимостей бэкенда `npm audit` сообщает 7 уязвимостей, включая 2 high и 2 critical; production-установка сообщает 2 high. Установленные зависимости фронтенда проверены без найденных уязвимостей. Обновление исходного backend-стека требует отдельного совместимого изменения с повторными тестами.

Для следующего этапа остаются согласование неполных денежных данных и политики округления с владельцем API, актуализация старых зависимостей, а для публичного окружения — аутентификация, управление секретами и ограничения доступа. Для большого объёма заказов полезны пакетная запись и хранение истории диагностических событий.
